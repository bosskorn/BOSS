# กติกาธุรกิจและโครงข้อมูล

ใช้เมื่อออกแบบหน้าที่มีสถานะ กติกา หรือข้อมูลข้ามหน้า เพื่อให้ทุกหน้าพูดเรื่องเดียวกัน
ที่มา: พฤติกรรมที่สังเกตได้จากการทดลองใช้ระบบคู่แข่ง ปรับชื่อและโครงให้เป็นของเรา

## สถานะออเดอร์

```
รอชำระ ──ยืนยันชำระ──▶ รอจัดส่ง ──เลือกขนส่ง──▶ รอพิมพ์ใบปะหน้า ──พิมพ์──▶ รอขนส่งเข้ารับ ──รับของ──▶ ส่งแล้ว
   │                        │
   └──หมดเวลา/ยกเลิก──▶ ยกเลิก ◀──ยกเลิก──┘
```

- ออเดอร์ COD ข้าม "รอชำระ" ไป "รอจัดส่ง" ทันที
- สถานะการชำระแยกจากสถานะออเดอร์: ยังไม่ชำระ · รอตรวจสลิป · ชำระบางส่วน · ชำระแล้ว · คืนเงินแล้ว
- "มีปัญหา" เป็นป้ายทับสถานะใดก็ได้ (ที่อยู่ไม่ครบ สต็อกไม่พอ ขนส่งรับไม่สำเร็จ) ต้องมีเหตุผลและปุ่ม "แก้แล้ว"
- ออเดอร์รอชำระถูกยกเลิกอัตโนมัติเมื่อเกินเวลาที่ร้านตั้ง (หน่วยชั่วโมง) และคืนสต็อก
- ทุกการเปลี่ยนสถานะบันทึกในประวัติ: ใคร ทำอะไร เมื่อไร

## กติกา CF (จับออเดอร์จากคอมเมนต์ไลฟ์)

- ทุก SKU มี **คีย์เวิร์ด CF** (เช่น `A01`) ลูกค้าพิมพ์คีย์เวิร์ดในคอมเมนต์เพื่อสั่ง
- จำนวน: `A01 2` หรือ `A01x2` = 2 ชิ้น
- **คำสั่งเพิ่ม:** ร้านกำหนดคำ (เช่น `เพิ่ม`) คอมเมนต์ "เพิ่ม A01" = เพิ่มจำนวนในออเดอร์เดิม
- **คำที่ให้ข้าม:** คอมเมนต์ที่มีคำเหล่านี้ไม่ถูกจับเป็นออเดอร์ (เช่น "ถาม", "ราคา")
- **สั่งทั้งชุด:** พิมพ์รหัสสินค้าหลัก + คำที่กำหนด = สั่งทุก SKU ของสินค้านั้นจำนวนเท่ากัน
- **ของขายเกิน:** เมื่อคอมเมนต์เข้ามาเกินสต็อก ร้านเลือกได้ว่าจะรับเป็น "ขายเกิน" (รอเติมของ) หรือปฏิเสธ และเลือกได้ว่าลูกค้าจะเห็นรายการขายเกินในลิงก์ออเดอร์หรือไม่
- ลูกค้าคนเดียวในรอบไลฟ์เดียวรวมเป็นออเดอร์เดียวจนกว่าจะชำระ
- เมื่อจับออเดอร์ได้ ระบบส่งข้อความส่วนตัวพร้อมลิงก์ออเดอร์ บางแพลตฟอร์มกำหนดว่าลูกค้าต้องทักมาก่อนร้านจึงส่งข้อความได้ ต้องออกแบบทางสำรอง (ตอบใต้คอมเมนต์ให้ลูกค้าทักแชต)
- สิทธิ์ที่ร้านเปิดให้ลูกค้าในลิงก์ออเดอร์: แก้สินค้า เลือกขนส่ง ฝากของ/รวมบิล

การ lock สต็อกต้องเกิดตอนจับคอมเมนต์ ไม่ใช่ตอนชำระ มิฉะนั้นจะขายเกินระหว่างไลฟ์

## เทมเพลตข้อความและตัวแปร

เหตุการณ์ที่มีเทมเพลต: ข้อความในลิงก์ออเดอร์ · สั่งซื้อสำเร็จ · จับออเดอร์จากไลฟ์ได้ · ออเดอร์ถูกแก้ไข · ชำระเงินสำเร็จ · จัดส่งแล้ว · ทวงยอด

ตัวแปรที่ใช้ได้ (แสดงเป็นชิปภาษาไทยในตัวแก้ข้อความ):
`{ชื่อลูกค้า}` `{ชื่อร้าน}` `{เลขออเดอร์}` `{รายการสินค้า}` `{จำนวนชิ้น}` `{ค่าส่ง}` `{ส่วนลด}` `{ยอดที่ต้องชำระ}` `{ยอดค้างชำระ}` `{ลิงก์ออเดอร์}` `{ธนาคาร}` `{เลขบัญชี}` `{ชื่อบัญชี}` `{เวลาสิ้นสุดการชำระ}` `{เวลาไลฟ์}` `{ที่อยู่จัดส่ง}` `{เบอร์โทร}` `{เลขพัสดุ}` `{หมายเหตุร้าน}`

จำกัด 2,000 ตัวอักษรต่อข้อความ แสดงตัวนับ และแสดงตัวอย่างด้วยข้อมูลจริงเสมอ

## กฎตอบอัตโนมัติ

ต่อกฎ: ชื่อ · เพจที่ใช้ · ลำดับความสำคัญ · ช่วงเวลาที่ทำงาน · หน่วงเวลาก่อนตอบ (นาที) · ความถี่ตอบซ้ำต่อคน (ชั่วโมง) · ช่องทางตอบ (ข้อความส่วนตัว / ตอบคอมเมนต์ / ทั้งสอง) · ชุดคีย์เวิร์ด → ข้อความ

## โครงข้อมูลหลัก

| สิ่ง | ข้อมูลสำคัญ |
|---|---|
| ร้าน (Shop) | ชื่อ ช่องทาง สถานะการเชื่อมต่อ วันหมดอายุ สิทธิ์ (ร้านค้า/ข้อความ/โฆษณา) |
| สินค้า (Product) | รหัส ชื่อ รูป คำอธิบาย หมวด แบรนด์ เปิดขาย |
| SKU | รหัส ตัวเลือก บาร์โค้ด คีย์เวิร์ด CF ราคาขาย ราคาป้าย ต้นทุน น้ำหนัก |
| สต็อก (Inventory) | SKU × คลัง: คงเหลือ จองแล้ว พร้อมขาย |
| การผูกช่องทาง (Listing) | SKU ↔ สินค้าในร้าน marketplace สถานะซิงก์ |
| ออเดอร์ (Order) | เลข ร้าน ที่มา (ไลฟ์/แชต/marketplace/สร้างเอง) สถานะ สถานะชำระ ยอดสินค้า ส่วนลด ค่าส่ง ยอดรวม COD หรือไม่ ผู้รับ ที่อยู่ ขนส่ง เลขพัสดุ หมายเหตุ ป้าย ผู้ดูแล รอบไลฟ์ |
| รายการในออเดอร์ | SKU ชื่อ ณ เวลาขาย ราคา จำนวน เป็นของแถมหรือไม่ |
| การชำระ (Payment) | ออเดอร์ วิธี จำนวน สลิป สถานะตรวจ เวลา |
| การคืนเงิน (Refund) | ออเดอร์ จำนวน ปลายทาง (ยอดคงเหลือ/บัญชีธนาคาร) เหตุผล |
| ลูกค้า (Customer) | ชื่อ บัญชีในแต่ละช่องทาง เบอร์ ที่อยู่หลายชุด ป้าย ยอดคงเหลือ |
| รอบไลฟ์ (Live session) | เพจ โพสต์ เวลา สินค้าในรอบ กติกา สถิติ |
| บทสนทนา (Conversation) | ลูกค้า ช่องทาง ประเภท (ข้อความ/คอมเมนต์) ป้าย สถานะตอบ ผู้รับผิดชอบ |
| ผู้ใช้ (User) | ชื่อ บทบาท สิทธิ์เมนู ร้านที่ดูแล |
| ประวัติ (Audit log) | ใคร ทำอะไร กับอะไร เมื่อไร ค่าเดิม→ค่าใหม่ |

## ช่องทางและบริการที่ต้องรองรับ

- **ลำดับแรก (ตลาดไทย):** Facebook Page / Instagram (ไลฟ์ + แชต), LINE OA, TikTok Shop, Shopee, Lazada
- **ถัดไป:** LINE SHOPPING, Shopify, WooCommerce
- **ชำระเงิน:** โอนธนาคาร + แนบสลิป, QR พร้อมเพย์/QR ธนาคาร, บัตรเครดิตผ่านผู้ให้บริการ, COD
- **ขนส่ง:** Flash Express, J&T Express, Kerry Express, ไปรษณีย์ไทย, Best Express, Ninja Van, SPX, DHL

ข้อจำกัดที่ดีไซน์ต้องรับมือ
- การเชื่อมต่อแต่ละแพลตฟอร์มหมดอายุได้ ต้องเตือนล่วงหน้าและมีปุ่มต่ออายุในทุกที่ที่ข้อมูลของร้านนั้นปรากฏ
- ข้อมูลจาก marketplace มาช้าได้ แสดง "ซิงก์ล่าสุดเมื่อ…" และปุ่มซิงก์เอง
- การพิมพ์ใบปะหน้าปริมาณมากมักต้องมีโปรแกรมช่วยพิมพ์บนเครื่อง ต้องมีสถานะ "เครื่องพิมพ์พร้อม/ไม่พร้อม" และทางสำรองเป็น PDF
